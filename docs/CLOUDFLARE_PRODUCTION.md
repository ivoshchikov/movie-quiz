# Hard Quiz production on Cloudflare

Prepared 8 November 2026 (Asia/Nicosia), roadmap task 6. The production artifact
is separate from the tested staging service. Source, CI and merge evidence are
recorded in [PR #73](https://github.com/ivoshchikov/movie-quiz/pull/73). A prepared
artifact or successful build is not proof that the public domain has switched.
Account-side setup and the actual domain cutover remain pending until verified.

## Deployment profiles

| Setting | Staging | Production |
| --- | --- | --- |
| Worker | `hard-quiz-staging` | `hard-quiz` |
| Wrangler config | `frontend/wrangler.jsonc` | `frontend/wrangler.production.json` |
| Git branch | `feat/cloudflare-staging` | `main`, after PR #73 is merged |
| Build | `npm run build:cloudflare` | `npm run build:cloudflare:production` |
| Deploy | `npm run deploy:cloudflare` | `npm run deploy:cloudflare:production` |
| Asset directory | `dist` | `dist-production` |
| Public documents | Global HTTP noindex | Indexable on the canonical domain |
| Private/game/error documents | noindex / no-store | noindex / no-store |
| workers.dev / version URLs | Controlled staging URL | Disabled in configuration |
| Analytics | GA4 build ID empty | Existing production GA4 ID |
| Domain | No custom domain | `hard-quiz.com`, attached only at cutover |

Keep the existing staging Worker. Do not attach the production domain to it or
change its build commands. The production configuration intentionally omits
`routes`: an initial deploy does not publish a domain or replace DNS. Wrangler's
explicit production config path selects the production name and output. The
Custom Domain is attached later through the dashboard, after private preflight.
With routes omitted, subsequent deploys do not submit route/custom-domain changes.

`workers_dev: false` and `preview_urls: false` disable alternate routes in the
production configuration. As a second layer, an absolute `_headers` rule marks
workers.dev asset responses noindex if those URLs are accidentally enabled later.
The local integration check sends a real HTTP Host to exercise that rule.

## Artifact and existing service settings

The normal Vite/postbuild sequence still generates prerendered public HTML,
RSS, sitemap and social images. Production preparation copies the finished build
to `dist-production`, adds its redirects/security/private-route headers and
records the profile in `seo-release.json`. The deployment guard rejects the wrong
profile, altered headers, fixture/test builds and unidentified source revisions.
It does not replace CI, an account inspection or post-cutover acceptance.

Production retains 33 legacy HTML redirects, true root/blog 404s, old social
endpoints and the production canonical origin. Static assets retain
`Strict-Transport-Security: max-age=63072000`, matching the Vercel baseline. The
small Worker explicitly adds that header to its generated error/API responses:
asset `_headers` do not apply to responses generated by Worker code.

Supabase URL, public client key, bucket, schema, RLS, game RPCs, Google provider
callback, production Auth Site URL and Daily's America/Chicago timezone stay in
place. No extra backend, database migration, paid plan, ad script or CMP is added
by this deployment. Existing GA4/first-party tracking behavior is preserved;
consent changes belong to roadmap task 11. Reusing tracking settings does not by
itself certify their future advertising compliance.

## One-time production Worker setup

The owner connected the Cloudflare plugin and the production Worker is already
configured. Use that connection for routine account checks and the automatic
main build for releases. The original setup steps below are retained for
recreation; no passwords or deployment tokens need to be pasted into chat.

1. Wait for PR #73 to be merged and the verified revision to exist on `main`.
2. Open **Workers & Pages → Create application → Connect GitHub**, reuse the
   existing GitHub connection and select `ivoshchikov/movie-quiz`.
3. Set these exact values. The project name must be `hard-quiz`, even if the UI
   infers the staging name from the repository's default Wrangler file.

   | Field | Value |
   | --- | --- |
   | Project / Worker name | `hard-quiz` |
   | Production branch | `main` |
   | Root directory / Path | `/frontend` |
   | Build command | `npm run build:cloudflare:production` |
   | Deploy command | `npm run deploy:cloudflare:production` |
   | Preview builds | Disabled |
   | Preview command, if a value is required | Leave its default; it is unused while previews are disabled |
   | Protect with Cloudflare Access | Disabled for the intended public production service |

4. In **Build variables and secrets**, configure the build variables below.
   Runtime Variables & Secrets alone do not supply values to a Vite build.

   | Name | Value source |
   | --- | --- |
   | `NODE_VERSION` | `22` |
   | `VITE_SITE_URL` | `https://hard-quiz.com` |
   | `VITE_SUPABASE_URL` | Same existing public project URL as staging/Vercel Production |
   | `VITE_SUPABASE_ANON_KEY` | Same existing public anon/publishable client key as staging/Vercel Production |
   | `VITE_SUPABASE_BUCKET` | Same existing bucket name as staging/Vercel Production |
   | `VITE_GA_ID` | Same ID as **Vercel → movie-quiz → Settings → Environment Variables → Production** |

   Do not add fixture values, `VITE_ANALYTICS_TEST_MODE=true`, `service_role`, a
   database password or a server secret. Do not set an empty GA ID in production.
   The build deliberately stops if required production values are missing or the
   key is a server-role key. Keep the real values in the service panels.

5. For the built-in deployment token choose **Create new token**, with a name
   such as `hard-quiz-builds`; let Cloudflare manage it. No manual token value is
   needed. Keep any token material inside Cloudflare.
6. Click **Deploy**. This creates the production service without attaching the
   website domain. Because alternate URLs are disabled, lack of a public
   workers.dev link is expected. Send the build status, selected branch and
   commands screenshot, with secret values hidden. The GitHub Cloudflare check
   can then be inspected independently.

Later pushes to the connected `main` branch automatically build and publish the
production Worker. The owner does not need to press Deploy for each release.
Keep the existing GitHub checks as the release gate before merging to main.

## Manual build revision failure

The owner's first production setup reached postbuild, then stopped with
`SEO build revision must be a full Git SHA`. That log does not disclose the
invalid metadata value. Source identity is now resolved from the actual checked-out
Git commit before automatic provider hints. Explicit `SEO_BUILD_REVISION` must
still be a full SHA; archive builds may use a complete provider SHA. Do not set
a permanent hard-coded commit ID in dashboard variables, pad a shortened hash or
disable the production guard. A normal source publication supplies the fix to
the connected main branch. Verify the new build, then continue account preflight;
retrying an old build can still use its old source revision.
The Git read trusts only the detected checkout path for that command, so shared
container ownership does not require a global Git configuration change.

## Before attaching the domain

Follow [the DNS cutover runbook](CLOUDFLARE_DNS_CUTOVER.md) in order. Retain a
fresh full zone export and inspect current routes/rules/free rule slots and
Active edge certificates covering both apex and www. Preserve the Google TXT,
NS and DNSSEC. Prepare/validate the canonical-host/HTTP redirect before proxying
www. A successful production build alone is insufficient for these private
checks. Refresh the READY Vercel release snapshot after merging this change;
keep Vercel and both domain associations until task 7 acceptance.

Only then attach **Custom Domain → hard-quiz.com** to **hard-quiz**. Verify actual
HTTPS, release identity, indexable public pages and private exclusions before
changing www. Do not manually CNAME the domain to workers.dev or apply the old
zone archive wholesale. The prepared rule and exact recovery order are in the
runbook. If the domain or certificate fails, recover before advancing.

## Task 7: production diagnostics

`wrangler.production.json` enables persisted invocation logs at 100%, traces at
10% and `redact_query_string`. Query parameters are removed before URL logging;
no new logging of headers, credentials or application payloads is added. Static
assets continue to bypass the user Worker except for the reviewed API/error
routes. Build/deployment guards, production canonical and HSTS stay unchanged.

After a successful main build, use the connected Cloudflare Observability API to
discover dataset keys/service values, query a narrow post-deployment window and
inspect request outcomes/errors. A normal read-only missing-page request can
verify invocation visibility without creating a game, account or analytics
observation. Empty historical results from the old disabled configuration do
not establish that no errors occurred. Sampling, free limits and retention also
limit later coverage; never report a guaranteed zero error rate from absent data.

No paid service or export destination is configured. Workers Free currently
includes 200,000 log events/day with three-day retention. Starting December 1,
2026, the announced Free shared allowance is 0.5 GB/day with seven-day retention;
ingestion stops at the daily cap, with no paid overage. Verify current terms
before changing plan or observability volume.
